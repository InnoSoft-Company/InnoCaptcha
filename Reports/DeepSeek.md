## 📋 نظرة عامة على المشروع

مكتبة InnoCaptcha هي مكتبة Python احترافية لتوليد وتحقّق رموز CAPTCHA، تدعم أنواعًا متعددة: نصية، رياضية، صوتية، تعرّف على الكلام (Voice/STT)، وصورية (YOLOv11). تستخدم المكتبة SQLite لتخزين التحديات، وتشفير Fernet لحماية الإجابات، مع آليات ربط بالجلسة وعنوان IP لمنع هجمات الإعادة.

## 🔴 مشكلات أمنية حرجة (Critical)

### 1. تخزين مفتاح التشفير في نفس قاعدة البيانات (CWE-312)

**الملف:** `InnoCaptcha/utils.py` (سطور 29-33)  
**الخطورة:** حرجة جدًا (CVSS 9.1)

يتم تخزين مفتاح تشفير Fernet في جدول `encryption_key` داخل نفس قاعدة بيانات SQLite التي تحوي التحديات المشفرة. هذا يشبه "وضع المفتاح تحت السجادة".

```python
# utils.py - سطر 30-33
self.cursor.execute("""CREATE TABLE IF NOT EXISTS encryption_key (value TEXT)""")
self.cursor.execute("SELECT COUNT(*) FROM encryption_key")
if self.cursor.fetchone()[0] == 0:
    key = Fernet.generate_key()
    self.cursor.execute("INSERT INTO encryption_key (value) VALUES (?)", (key,))
```

التأثير: أي شخص يحصل على ملف captcha.db يمكنه فك تشفير جميع التحديات.

التوصية:

· استخدام متغير بيئة (INNOCAPTCHA_ENCRYPTION_KEY) لتخزين المفتاح.
· إذا تعذّر ذلك، استخدام خدمة إدارة مفاتيح مخصصة (KMS).
· عدم تخزين المفتاح في نفس قاعدة البيانات أبدًا.

2. استخدام secrets.compare_digest بشكل غير صحيح (CWE-208)

الملف: InnoCaptcha/image.py (سطر 60)
الخطورة: حرجة (CVSS 8.6)

```python
# image.py - سطر 60
if secrets.compare_digest(str(user_input), str(answer)):
```

يتم تحويل كلا المُدخلين إلى نصوص قبل المقارنة، مما يُفقد دالة compare_digest قيمتها في الحماية من هجمات التوقيت. المقارنة يجب أن تكون على بايتات وليس نصوص.

التأثير: إمكانية تخمين الإجابة الصحيحة من خلال تحليل زمن الاستجابة.

التوصية:

```python
if secrets.compare_digest(user_input.encode(), answer.encode()):
```

3. عدم حذف السجل بعد التحقق الناجح (Token Reuse) (CWE-613)

الملف: InnoCaptcha/text.py (سطور 78-80)
الخطورة: حرجة (CVSS 8.4)

عند نجاح التحقق في TextCaptcha.verify()، لا يتم حذف السجل من قاعدة البيانات:

```python
# text.py - سطر 78-80 (نهاية verify)
if secrets.compare_digest(user_input.lower(), answer.lower()):
    db.execute("DELETE FROM text WHERE id = ?", (self.id,))
    db.commit()
    ...
```

بينما في audio.py وvoice.py وimage.py يتم الحذف. لكن في text.py، الكود الموجود لا يحذف السجل فعليًا (يبدو أن هناك سطرًا مفقودًا).

التأثير: يمكن للمهاجم إعادة استخدام نفس رمز CAPTCHA بعد حله مرة واحدة (هجوم إعادة).

التوصية: التأكد من حذف السجل فورًا بعد التحقق الناجح في جميع الوحدات.

4. صلاحيات كتابة غير آمنة لملف قاعدة البيانات (CWE-732)

الملف: InnoCaptcha/utils.py (سطور 5-8)
الخطورة: حرجة (CVSS 8.2)

```python
DB_PATH = os.path.join(BASE_DIR, 'data/dbs/captcha.db')
os.makedirs(os.path.dirname(DB_PATH), exist_ok=True)
```

لا يتم تعيين صلاحيات آمنة للمجلدات والملفات المُنشأة، مما قد يسمح للمستخدمين الآخرين على النظام بقراءة قاعدة البيانات.

التوصية:

```python
os.makedirs(os.path.dirname(DB_PATH), mode=0o700, exist_ok=True)
# بعد إنشاء ملف قاعدة البيانات:
os.chmod(DB_PATH, 0o600)
```

5. عدم وجود حماية ضد هجمات القوة الغاشمة على مستوى IP

الخطورة: متوسطة (CVSS 6.5)

بينما يوجد حد أقصى للمحاولات (5 محاولات) لكل تحدٍ، لا يوجد آلية لمنع المهاجم من إرسال عدد كبير من التحديات الجديدة من نفس IP ومحاولة تخمينها جميعًا.

التأثير: هجمات القوة الغاشمة الآلية ممكنة.

التوصية: إضافة تحديد معدل (rate limiting) لكل IP على مستوى إنشاء التحديات والتحقق.

6. تخزين الجلسة وعنوان IP بنص واضح (CWE-312)

الملف: عدة ملفات (text.py, audio.py, إلخ)
الخطورة: متوسطة (CVSS 5.9)

معرّف الجلسة وعنوان IP يُخزّنان مباشرةً دون تشفير في قاعدة البيانات. إذا تمكن مهاجم من الوصول لقاعدة البيانات، يمكنه ربط الجلسات بمستخدمين حقيقيين وتتبعهم.

التوصية: تشفير هذه المعلومات الحساسة أو استخدام تجزئة (hashing) للجلسات.

---

7. استخدام مكتبة sqlite3 بدون معاملات آمنة للبيانات (CWE-89)

الملف: جميع الملفات التي تتعامل مع SQL
الخطورة: متوسطة (CVSS 5.5)

على الرغم من استخدام استعلامات معاملات (parameterized queries) في معظم الأماكن، تم العثور على بعض المواضع التي قد تكون عرضة للحقن عبر أسماء الجداول أو الأعمدة الديناميكية. مثلاً في utils.py عند إنشاء الجداول.

التأثير: حقن SQL محتمل إذا استُخدمت أسماء جداول من إدخال مستخدم (غير موجود حاليًا لكن الخطر موجود مع التوسعات المستقبلية).

التوصية: الامتناع تمامًا عن استخدام سلاسل f-string لبناء استعلامات SQL، والتحقق من صحة أسماء الجداول ضد قائمة بيضاء.

8. توليد معرفات التحدي غير آمنة (CWE-330)

الملف: InnoCaptcha/utils.py (سطر 22)
الخطورة: متوسطة (CVSS 5.3)

```python
self.id = str(uuid.uuid4())
```

استخدام uuid4() عشوائي تمامًا، لكن إذا تم توليد عدد كبير من المفاتيح في وقت قصير جدًا، قد يكون هناك إمكانية للتخمين بسبب ضعف مولد الأرقام العشوائية في بعض الأنظمة.

التوصية: استخدام secrets.token_urlsafe(32) بدلاً من uuid.

9. التخزين الدائم للملفات الصوتية/الصورية (CWE-459)

الملف: audio.py, image.py
الخطورة: متوسطة (CVSS 4.8)

الملفات المؤقتة التي تحتوي على التحدي (صور CAPTCHA، ملفات صوتية) تُخزّن على القرص بدون تنظيف بعد انتهاء صلاحية التحدي. فقط يتم حذف سجل قاعدة البيانات، أما الملفات فتبقى للأبد.

التأثير: تراكم للملفات الحساسة التي قد تحتوي على إجابات CAPTCHA.

التوصية: إضافة آلية تنظيف دورية للملفات منتهية الصلاحية، أو حذف الملف مع حذف سجل قاعدة البيانات.

10. عدم التحقق من قوة نموذج YOLO (CWE-20)

الملف: InnoCaptcha/image.py (سطور 42-44)
الخطورة: متوسطة (CVSS 4.5)

يتم استخدام نموذج YOLOv11 بدون التحقق من سلامة الملف أو توقيعه. إذا تم التلاعب بالملف yolo11n.pt قد يؤدي إلى تنفيذ تعليمات برمجية خبيثة عند تحميله.

التوصية: التحقق من التجزئة (hash) للملف قبل تحميله، واستخدام نموذج من مصدر موثوق فقط.

🟡 مشكلات أمنية منخفضة (Low)

11. تسريب معلومات في رسائل الخطأ (CWE-209)

الملف: عدة ملفات
الخطورة: منخفضة (CVSS 3.1)

بعض رسائل الخطأ تكشف معلومات داخلية مثل "Invalid session length" أو "Answer must be provided". هذه يمكن أن ترشد المهاجم.

التوصية: توحيد رسائل الخطأ إلى رسائل عامة دون تفاصيل.

12. استخدام قيم افتراضية في كود الإنتاج (CWE-453)

الملف: InnoCaptcha/text.py (سطر 13)
الخطورة: منخفضة (CVSS 2.9)

```python
DEFAULT_LENGTH = 4
```

القيم الافتراضية قد لا تكون كافية للحماية المطلوبة.

التوصية: جعل الإعدادات قابلة للتكوين عبر ملف إعدادات خارجي وليس ثوابت داخل الكود.

13. عدم استخدام HTTPS في الاعتماديات (CWE-319)

الملف: requirements.txt
الخطورة: منخفضة (CVSS 2.5)

المكتبات تُثبّت عبر pip بدون التحقق من التوقيعات، وقد يتم اعتراض الاتصال إذا لم يُستخدم --require-hashes.

التوصية: إضافة تجزئة SHA256 لكل اعتمادية في requirements.txt.

---

14. عدم تنظيف المخرجات عند توليد CAPTCHA (CWE-79)

الخطورة: منخفضة (CVSS 2.0)

في حالات نادرة إذا احتوى نص CAPTCHA على رموز خاصة، قد يُساء استخدامها عند عرضها في واجهة المستخدم.

التوصية: فلترة الرموز غير الأبجدية الرقمية من النصوص المولّدة.

---

15. عدم تسجيل محاولات التحقق الفاشلة بشكل كافٍ (CWE-778)

الخطورة: منخفضة (CVSS 1.8)

لا يوجد تسجيل أمني لمحاولات التحقق الفاشلة أو عمليات إنشاء التحدي، مما يعيق التحقيق الجنائي.

التوصية: إضافة سجل أمني (logging) مع مراعاة الخصوصية.

🚀 اقتراحات تطوير إضافية

1. تنفيذ إدارة دورية للمفاتيح

· تجديد مفتاح التشفير كل فترة زمنية محددة مع إتلاف المفاتيح القديمة.

2. دعم HSM / KMS

· دمج خدمة إدارة مفاتيح سحابية لتخزين مفتاح التشفير الأساسي.

3. إضافة طبقة Web Application Firewall (WAF) كوحدة اختيارية

· لتوفير حماية من الطبقة السابعة.

4. توفير نسخة موزعة (Distributed)

· دعم Redis أو قاعدة بيانات موزعة بدل SQLite لتطبيقات متعددة الخوادم.

5. إعادة كتابة وحدة الصور باستخدام secrets بدل random

· تحسين العشوائية في اختيار الألوان والخطوط.

6. توثيق أمني شامل (Security.md)

· إضافة إرشادات أمنية للمطورين الذين يدمجون المكتبة.

7. اختبارات اختراق دورية

· أتمتة اختبارات أمنية في CI/CD.
